1
Stage 01 · Research & Architecture Design

Feasibility Study & System Design

Both sides investigated whether connecting a live production line to a virtual commissioning environment via IoT was technically feasible and designed the architecture to do it.

Complete OPC-UA MQTT Purdue Model
IoT Side — What was researched
  • Evaluated OPC-UA as the acquisition protocol from the Festo CP Lab.
  • Investigated MQTT as the cloud transport layer.
  • Reviewed the Purdue Model for OT/IT cybersecurity separation.
  • Selected HiveMQ Cloud as broker for MQTT over TLS support.
Virtual Commissioning Side — What was researched
  • Reviewed Siemens NX MCD as the digital twin environment.
  • Confirmed TIA Portal V20 + PLCSIM Advanced as the PLC emulation stack.
  • Identified Simatic Robotic Suite as the robot programming layer.
  • Defined OPC-UA as the handshake protocol.
Architecture Decision

The two-PC architecture was defined: PC 1 handles physical data acquisition; PC 2 is dedicated to the virtual environment. HiveMQ acts as the secure bridge.

2
Stage 02 · IoT Side — Festo PC

OPC-UA Server & Node-RED Pipeline

Setting up the data acquisition side: extracting live CP Lab data via OPC-UA, validating the acquired data, transforming it in Node-RED, and publishing to HiveMQ via MQTT over TLS.

Complete OPC-UA Node-RED HiveMQ
OPC-UA Server Setup
  • Selected relevant signals to extract from the live CP Lab sensor/actuator data.
  • Validated the selected signals using the OPC UA Expert client to verify their reliability before acquiring them through Node-RED.
  • Configured the signal acquisition pipeline in Node-RED.
Node-RED: JSON → OPC-UA Transform
  • Transformed the signals acquired by the OPC UA client node into a JSON payload for transmission to the MQTT broker.
  • Received the MQTT JSON payload on the Virtual Commissioning PC and transformed it into structured OPC UA nodes.
  • Ensured that “undefined” values from non-updated signals during OPC UA acquisition from the Festo CP Lab were not transmitted to the broker; instead, the last valid data value was retained and sent.
MQTT/TLS — HiveMQ

Configured the MQTT broker with TLS encryption and authentication in accordance with the Purdue Model, enabling secure reception of publications from PC 1 and delivery to subscribers on PC 2.

OPC UA Data Pipeline Validation

The initial connection to the data received by the MQTT broker and subsequently transformed into OPC UA nodes was originally intended to be accessed through an OPC UA client configured in TIA Portal and simulated using PLC SIM Advanced. However, the university computers hosting TIA Portal, Siemens NX, SRPS, and PLC SIM Advanced required institution-specific licenses and did not provide administrator privileges, preventing the installation of Node-RED and its OPC UA nodes on those machines.

To validate the communication pipeline, Node-RED was instead installed on a personal computer. The OPC UA server configured within Node-RED was then accessed using UA Expert to verify the integrity and reliability of the data exchange with the Virtual Commissioning PC.

Outcome: End-to-end data flow validated. Communication confirmed with UA Expert as OPC-UA client on the Virtual Commissioning PC.

Stage 03 · Virtual Side - Virtual Commissioning PC

Siemens NX Digital Twin & Robot Programming

Building the virtual commissioning environment: configuring the NX digital twin, programming the robot in Simatic Robotic Suite, and mapping I/O signals.

Complete Siemens NX Simatic Robotic Suite Signal Mapping
Simatic Robotic Suite
  • Imported reference frame for CP Lab output station.
  • Defined and validated robot pickup points.
  • Programmed point path sequence vendor-agnostic configuration.
Siemens NX Configuration
  • Implemented the physical and control configuration of the imported CAD modules in Siemens NX, including kinematic constraints, rigid bodies, collision sensors, and actuator controls to reproduce real system behavior.
  • Replicated robot positioning inside NX MCD model.
  • Configured all signals: inputs from PLC, outputs to PLC.
  • Validated NX response matches physical behaviour.
NX ↔ Robotic Suite Integration

Robot movements programmed in Simatic Robotic Suite reflected in NX simulation in real time via shared signal interface.

Outcome: Robot program validated. NX ↔ Robotic Suite communication confirmed both respond correctly to PLC signals.

Stage 04 · Integration — Both sides

TIA Portal & Full System Validation

Connecting the IoT data pipeline to the virtual commissioning environment: programming the PLC and demonstrating the full system working end-to-end.

Complete TIA Portal V20 PLCSIM Advanced Licensing constraints
TIA Portal V20
  • Programmed PLC logic for full cell sequence.
  • Configured OPC-UA server within TIA Portal.
  • Mapped PLC tags to NX signal interface.
OPC-UA Handshake Validation
  • OPC UA Client configuration deployed in TIA Portal to subscribe to the server implemented in the Virtual Commissioning PC in Node-RED
Licensing and Admin rights Workaround

As mentioned in Stage 2, the university computers containing the licensed software required for the project did not provide administrator privileges. As a result, direct access to the signals transmitted through the MQTT broker could not be established on those systems. Nevertheless, the communication handshake and signal exchange were successfully validated using UA Expert, as described previously.

Furthermore, implementing the complete automated solution required access to the robot HMI, in TIA Portal, to retrieve the execution signals associated with the programmed robot paths. However, the HMI licenses for the robotic system had expired, preventing direct integration and testing. To overcome this limitation, a simulated environment was developed to visualize the robot executing the programmed trajectories, along with a separate simulation of the output station of the Festo CP Lab system.

The steps described in this stage represent the logical continuation and intended deployment process for the complete project implementation under fully operational conditions and with unrestricted access to the required software and hardware resources.

Outcome: The feasibility of the proposed system was demonstrated using the available software tools under simulated and constrained deployment conditions. NX ↔ Simatic Robotic Suite ↔ TIA Portal communication confirmed.

Key Findings

01
IoT Handshake Works

End-to-end OPC-UA → Node-RED → MQTT/TLS → HiveMQ → OPC-UA data flow was validated. Real CP Lab data travels to the virtual environment correctly, with data types and node addresses preserved across the protocol boundary.

Validated ✓
02
Virtual Cell is Functional

NX, Simatic Robotic Programming Suite and TIA Portal work together as expected. Signals are sent and received correctly. The robot performs its programmed sequence. The digital twin responds to PLC commands as the physical system would.

Validated ✓
03
JSON→OPC-UA transformation

One of the most technically demanding steps was transforming MQTT JSON payloads into OPC-UA structured data. Node-RED solves this elegantly, but requires careful field mapping and data formatting to maintain integrity across protocols.

Key insight
04
Vendor-Agnostic by Design

Simatic Robotic Programming Suite supports KUKA, ABB, Fanuc, and others, not just Siemens robots. OPC-UA and MQTT are open standards used in an open source platform (Node-RED). The architecture is not locked to any vendor and can be replicated with different hardware combinations.

Architecture strength
05
Cybersecurity Matters

MQTT over TLS on HiveMQ Cloud with authentication, following the Purdue Model, provides a solid baseline. The architecture naturally separates OT (physical line) from IT (cloud and virtual env), reducing attack surface. However, further cybersecurity measures can be implemented by adding VPNs and firewalls layers.

Reproduciblity Considerations
University Admin Rights Our Project

Access to the university’s development workstations was restricted due to the absence of administrator privileges. This prevented the installation and configuration of required middleware and communication tools, such as Node-RED OPC UA nodes. As a result, direct deployment and testing of the full MQTT-to-OPC UA communication pipeline on the target systems could not be performed, requiring the use of an external personal computer for communiction protocol validation.

Workaround applied ✓
HMI License Expiry Our Project

The TIA Portal HMI license expired, preventing the execution of a full end-to-end run with the full automation solution implemented in the IoT Virtual Commissioning environment. To address this limitation, a workaround PLC program was developed. On one side, the automatic operation of the cell was demonstrated, and on the other, the communication handshake between SRPS and Siemens NX was depicted. However, due to the absence of the HMI trigger, the intended full automation workflow could not be completely implemented.

Workaround applied ✓
Licensing Costs Reproducibility Considerations

Reproducibility is limited by the need for licensed proprietary tools, including TIA Portal, Siemens NX, PLC SIM Advanced, and SRPS. These tools are essential for PLC programming, simulation, CAD-based virtual commissioning, and robotic validation, but their high licensing costs can make them difficult to access for smaller companies and research groups.

Replicable-with-conditions
IoT infrastructure Reproducibility Considerations

Reproducibility of this system assumes the availability of a pre-existing IoT infrastructure within the deployment environment, as its setup is outside the scope of this implementation. While the communication protocols were implemented and the signals were selected and validated as part of this project, the OPC UA server deployment on the source PLC, as well as the PC already connected to the PLC, were already in place prior to the start of the implementation.

Replicable-with-conditions
Network / infrastructure dependency Reproducibility Considerations

Replicability depends on stable internet connectivity and configurable firewall/NAT rules to allow MQTT over TLS communication via HiveMQ and OPC UA tunneling across network boundaries. Industrial environments with strict network segmentation may require additional configuration not covered in this implementation.

Replicable-with-conditions
Latency and Synchronization Constraints Reproducibility Considerations Our Project

Due to the distributed nature of MQTT over internet-based brokers and OPC UA polling intervals, slight latency exists between physical system state changes and digital twin updates. This may affect strict real-time synchronization in high-speed automation scenarios.

real-time-approximate-synchronization
Scalability Constraints Reproducibility Considerations Our Project

While the architecture is scalable in principle, performance depends on network bandwidth, broker capacity, and OPC UA subscription load. Large-scale deployments may require distributed broker architectures or load balancing strategies.

Scalable-with-conditions

None of these constraints invalidate the core finding, the architecture works and is replicable.
