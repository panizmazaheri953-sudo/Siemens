S1
Stage 01 · Research & Architecture Design

Feasibility Study & System Design

Both sides of the team investigated whether connecting a live production line to a virtual commissioning environment via IoT was technically feasible — and designed the architecture to do it.

Complete OPC-UA MQTT Purdue Model Both sides
IoT Side — What was researched
  • Evaluated OPC-UA as the acquisition protocol from the Festo CP Lab — chosen for its structured data model and compatibility with industrial systems.
  • Investigated MQTT as the cloud transport layer — chosen for its lightweight pub/sub model, perfect for IoT over unreliable networks.
  • Reviewed the Purdue Model for OT/IT cybersecurity separation: physical layer, control layer, and cloud layer should be isolated.
  • Selected HiveMQ Cloud as broker for its MQTT over TLS support and free tier for prototyping.
Virtual Commissioning Side — What was researched
  • Reviewed Siemens NX MCD (Mechatronic Concept Designer) as the digital twin environment for signal-based simulation.
  • Confirmed TIA Portal V20 + PLCSIM Advanced as the PLC emulation stack — enabling virtual PLC running without physical hardware.
  • Identified Simatic Robotic Suite as the robot programming layer — key advantage: vendor-agnostic, supports multiple robot brands.
  • Defined OPC-UA as the handshake protocol between the MQTT subscriber and the virtual PLC.
Architecture Decision

The two-PC architecture was defined: PC 1 handles all physical data acquisition; PC 2 is fully dedicated to the virtual environment. HiveMQ acts as the secure bridge between them, keeping OT and IT layers separated per the Purdue Model.

Key challenge identified early

The main technical challenge anticipated: data format translation. MQTT delivers JSON payloads; OPC-UA on PC 2 expects a structured node model. Node-RED was selected as the transformation middleware to bridge this gap.

S2
Stage 02 · IoT Side — PC 1

OPC-UA Server & Node-RED Pipeline

Setting up the data acquisition side: extracting live CP Lab data via OPC-UA, transforming it in Node-RED, and publishing to HiveMQ via MQTT over TLS.

Complete OPC-UA Node-RED HiveMQ PC 1
OPC-UA Server Setup
  • Configured the OPC-UA server connected to the Festo CP Lab to expose live sensor and actuator data as addressable nodes.
  • Mapped relevant process variables (conveyor states, sensor readings, station signals) to OPC-UA node addresses.
  • Tested direct OPC-UA subscription using UA Expert to confirm data was being published correctly before moving to Node-RED.
Node-RED: JSON → OPC-UA Transform
  • MQTT messages from HiveMQ arrive as raw JSON payloads — OPC-UA on PC 2 cannot consume JSON directly.
  • Node-RED flow extracts fields from the JSON object and maps each value to the corresponding OPC-UA node address.
  • This was the most technically demanding transformation: maintaining data types (bool, int, float) across the protocol boundary.
  • Tested multiple Node-RED node configurations until data integrity was confirmed end-to-end.
MQTT/TLS — HiveMQ Configuration

MQTT broker configured on HiveMQ Cloud with TLS encryption. Credentials and certificates managed per Purdue Model security requirements. The broker receives publications from PC 1 and delivers them to subscribers on PC 2. Connection stability was tested across sessions.

Constraint encountered

University computers do not grant admin rights — Node-RED with OPC-UA nodes could not be installed on the lab machines directly. The pipeline was designed and validated on personal hardware, and the OPC-UA behaviour was demonstrated using UA Expert as a subscriber proxy.

S3
Stage 03 · Virtual Side — PC 2

Siemens NX Digital Twin & Robot Programming

Building the virtual commissioning environment: configuring the NX digital twin of the CP Lab, programming the robot in Simatic Robotic Suite, and mapping all I/O signals for PLC synchronisation.

Complete Siemens NX Simatic Robotic Suite Signal Mapping PC 2
Simatic Robotic Suite — Robot Programming
  • Imported the reference frame for the CP Lab output station into Simatic Robotic Suite.
  • Defined and validated the robot pickup points — the exact Cartesian coordinates where the robot must pick and place parts.
  • Programmed the point path sequence: the ordered list of positions the robot travels through for each cycle.
  • Simatic Robotic Suite is vendor-agnostic — this same configuration can be applied to robots from KUKA, ABB, Fanuc, and others, not just Siemens hardware.
Siemens NX — Digital Twin Configuration
  • Replicated the robot positioning defined in Simatic Robotic Suite inside the Siemens NX MCD model.
  • Configured all relevant signals in the NX file: input signals (triggers from PLC) and output signals (feedback to PLC).
  • Each conveyor station, sensor, and actuator from the physical CP Lab was represented as a kinematic body with associated signal connections.
  • The NX model was validated to confirm it responds correctly when signals are toggled — matching expected physical behaviour.
NX ↔ Simatic Robotic Suite Integration

The NX environment and Simatic Robotic Suite share a common signal interface. Robot movements programmed in Simatic Robotic Suite are reflected in the NX simulation in real time. This was validated by sending signals from TIA Portal through PLCSIM Advanced and observing correct movement response in both environments simultaneously.

Design decision: no supports

The robot program was built to operate without relying on HMI trigger signals as a contingency plan — anticipating the licensing issue with HMI that was later encountered. This allowed the cell to demonstrate full automatic functioning despite the constraint.

S4
Stage 04 · Integration — Both sides

TIA Portal Programming & Full System Validation

Connecting the IoT data pipeline to the virtual commissioning environment: programming the PLC in TIA Portal, validating the OPC-UA handshake, and demonstrating the full system working end-to-end.

Complete TIA Portal V20 PLCSIM Advanced Licensing constraints Both sides
TIA Portal V20 — PLC Programming
  • Programmed the PLC logic in TIA Portal V20 to control the full cell sequence: conveyor movements, station triggers, and robot activation.
  • Configured the OPC-UA server within TIA Portal so that the PLC's data model is exposed and subscribable by external clients.
  • Mapped PLC output tags to the NX signal interface — each signal in NX corresponds to a tag in the TIA Portal program.
  • PLCSIM Advanced runs the PLC program virtually — no physical hardware required for validation.
OPC-UA Handshake Validation
  • The intended validation was: CP Lab OPC-UA data → Node-RED → MQTT → HiveMQ → PC 2 → OPC-UA to TIA Portal.
  • Due to university admin rights restrictions, TIA Portal could not be installed on lab PCs and Node-RED OPC-UA nodes were inaccessible.
  • Workaround: UA Expert was used as an OPC-UA subscriber to simulate the PLC subscriber behaviour — confirming that data arrives correctly at the OPC-UA endpoint on PC 2.
  • The OPC-UA handshake was fully validated: data structure, node addresses, and data types confirmed correct.
HMI Licensing Issue & Workaround

The university's Siemens license expired mid-project, removing access to the HMI component. The HMI was the intended source of the trigger signal that activates the robot's point path sequence. Workaround: an alternative PLC program was developed that demonstrates automatic cell functioning — all components (conveyor, robot, NX twin) operate in sequence, demonstrating full system feasibility even without the HMI trigger.

What was demonstrated
  • NX and Simatic Robotic Suite working simultaneously with correct signal exchange.
  • PLC signals correctly driving robot movements visible in both virtual environments.
  • OPC-UA data flow validated end-to-end with UA Expert.
  • Automatic cell cycle functioning — demonstrating the full architecture is viable.

Key Findings

01
IoT Handshake Works

End-to-end OPC-UA → Node-RED → MQTT/TLS → HiveMQ → OPC-UA data flow was validated. Real CP Lab data travels to the virtual environment correctly, with data types and node addresses preserved across the protocol boundary.

Validated ✓
02
Virtual Cell is Functional

NX, Simatic Robotic Suite and TIA Portal work together as expected. Signals are sent and received correctly. The robot performs its programmed sequence. The digital twin responds to PLC commands as the physical system would.

Validated ✓
03
JSON→OPC-UA is the Hard Part

The most technically demanding step was transforming MQTT JSON payloads into OPC-UA structured data. Node-RED solves this elegantly — but requires careful field mapping and data-type management to maintain integrity across protocols.

Key insight
04
Licensing is a Real Barrier

University licensing and admin rights restrictions prevented full end-to-end PLC validation on lab machines. This is a real-world constraint any organisation faces — the project demonstrates why open protocols (OPC-UA, MQTT) reduce vendor dependency.

Constraint
05
Vendor-Agnostic by Design

Simatic Robotic Suite supports KUKA, ABB, Fanuc, and others — not just Siemens robots. OPC-UA and MQTT are open standards. The architecture is not locked to any vendor and can be replicated with different hardware combinations.

Architecture strength
06
Cybersecurity Matters

MQTT over TLS on HiveMQ Cloud, following the Purdue Model, provides a solid baseline. The architecture naturally separates OT (physical line) from IT (cloud and virtual env), reducing attack surface — though VPN and firewall layers would strengthen it further.
