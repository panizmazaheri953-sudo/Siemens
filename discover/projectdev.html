1
Stage 01 · Research & Architecture Design

Feasibility Study & System Design

Both sides investigated whether connecting a live production line to a virtual commissioning environment via IoT was technically feasible — and designed the architecture to do it.

Complete OPC-UA MQTT Purdue Model
IoT Side — What was researched
  • Evaluated OPC-UA as the acquisition protocol from the Festo CP Lab.
  • Investigated MQTT as the cloud transport layer.
  • Reviewed the Purdue Model for OT/IT cybersecurity separation.
  • Selected HiveMQ Cloud as broker for MQTT over TLS support.
Virtual Commissioning Side — What was researched
  • Reviewed Siemens NX MCD as the digital twin environment.
  • Confirmed TIA Portal V20 + PLCSIM Advanced as the PLC emulation stack.
  • Identified Simatic Robotic Suite as the robot programming layer.
  • Defined OPC-UA as the handshake protocol.
Architecture Decision

The two-PC architecture was defined: PC 1 handles physical data acquisition; PC 2 is dedicated to the virtual environment. HiveMQ acts as the secure bridge.

2
Stage 02 · IoT Side — PC 1

OPC-UA Server & Node-RED Pipeline

Setting up the data acquisition side: extracting live CP Lab data via OPC-UA, transforming it in Node-RED, and publishing to HiveMQ via MQTT over TLS.

Complete OPC-UA Node-RED HiveMQ
OPC-UA Server Setup
  • Configured OPC-UA server to expose live CP Lab sensor/actuator data.
  • Mapped process variables to OPC-UA node addresses.
  • Tested direct subscription using UA Expert.
Node-RED: JSON → OPC-UA Transform
  • MQTT JSON payloads transformed to OPC-UA structured nodes.
  • Maintained data types (bool, int, float) across protocol boundary.
MQTT/TLS — HiveMQ

Broker configured with TLS encryption per Purdue Model. Receives publications from PC 1, delivers to subscribers on PC 2.

Outcome: End-to-end data flow validated. Communication confirmed with UA Expert as OPC-UA client on PC 2.

Key Findings

01
IoT Handshake Works

End-to-end OPC-UA → Node-RED → MQTT/TLS → HiveMQ → OPC-UA data flow was validated. Real CP Lab data travels to the virtual environment correctly, with data types and node addresses preserved across the protocol boundary.

Validated ✓
02
Virtual Cell is Functional

NX, Simatic Robotic Suite and TIA Portal work together as expected. Signals are sent and received correctly. The robot performs its programmed sequence. The digital twin responds to PLC commands as the physical system would.

Validated ✓
03
JSON→OPC-UA is the Hard Part

The most technically demanding step was transforming MQTT JSON payloads into OPC-UA structured data. Node-RED solves this elegantly — but requires careful field mapping and data-type management to maintain integrity across protocols.

Key insight
04
Licensing is a Real Barrier

University licensing and admin rights restrictions prevented full end-to-end PLC validation on lab machines. This is a real-world constraint any organisation faces — the project demonstrates why open protocols (OPC-UA, MQTT) reduce vendor dependency.

Constraint
05
Vendor-Agnostic by Design

Simatic Robotic Suite supports KUKA, ABB, Fanuc, and others — not just Siemens robots. OPC-UA and MQTT are open standards. The architecture is not locked to any vendor and can be replicated with different hardware combinations.

Architecture strength
06
Cybersecurity Matters

MQTT over TLS on HiveMQ Cloud, following the Purdue Model, provides a solid baseline. The architecture naturally separates OT (physical line) from IT (cloud and virtual env), reducing attack surface — though VPN and firewall layers would strengthen it further.

Every prototype has boundaries. These are the constraints encountered — and what they mean for real-world replication.

1 Scope boundary
01
HMI License Expiry Licensing

The TIA Portal HMI license expired mid-project, preventing a full HMI-triggered end-to-end run. A workaround PLC program was developed that demonstrates automatic cell operation without the HMI trigger — the core functionality is preserved, but the intended human-machine interface layer could not be validated in the final demo.

Workaround applied ✓
02
University Admin Rights Licensing

Restricted admin rights on university machines limited software installation flexibility. Some components had to be configured around system policies rather than optimally. This is a realistic constraint any organisation faces when deploying in managed IT environments — and it reinforces the case for open, standards-based protocols that don't require deep system access.

Navigated — not resolved
03
PLCSIM Advanced — Single Instance Licensing

PLCSIM Advanced only permits one virtual PLC instance at a time under the available license tier. This prevented testing multiple concurrent virtual controllers simultaneously, which would be relevant for larger multi-cell environments. A production deployment would require higher-tier licensing or physical PLC hardware.

Out of scope for this prototype
04
Two-PC Dependency Infrastructure

The architecture separates physical acquisition (PC 1) and virtual commissioning (PC 2) across two machines. While this follows a sound network security model, it introduces a physical dependency — both machines must be available and networked for the system to function. A containerised or cloud-hosted deployment could remove this constraint.

Design decision — not a flaw
05
No Bidirectional Feedback Loop Infrastructure

Data currently flows from the physical line to the virtual environment. The reverse — virtual environment sending commands back to the physical CP Lab — was not implemented. A full closed-loop system would require bidirectional OPC-UA write access to the physical PLC, which introduces safety and access control considerations beyond this project's scope.

Future work
06
Prototype Scope — Not Production Scale Scope

This is a proof-of-concept demonstrating feasibility, not a production-hardened deployment. Considerations such as redundancy, failover, latency profiling under load, formal cybersecurity audit, and enterprise-scale signal volumes were not addressed. The architecture is sound as a foundation — but scaling it would require additional engineering effort in each of those areas.

Known & intentional

None of these constraints invalidate the core finding — the architecture works and is replicable.
